# Design decisions & PRD reconciliation

Where the PRD, the starter, or the backlog conflicted, the conflict was flagged and resolved with the product owner
before building. This is the record of what was decided and how it is implemented.

| # | Conflict | Decision (as built) |
|---|---|---|
| 1 | Holders vs. login users (§8, §5) | One `holders` table (person, team, department, job_site, other). A person need not have an account; an account links to exactly one person holder. The ledger stores one `holder_id`. |
| 2 | Asset state vs. condition (§12 vs §15.2) | Exactly the six §12 states (`available, checked_out, lost, damaged, under_repair, retired`) plus a separate condition (`good, damaged, needs_inspection, replaced`). Mapping on return: good→available, damaged→damaged, needs_inspection→under_repair, replaced→retired. `archived_at` is a separate visibility flag (§51). |
| 3 | Corrections (§24, §50) | A `CORRECTION` ledger type: a reversal row linked to the original (+ optional replacement row). Refused (409 `CORRECTION_BLOCKED`) if later activity depends on the original. One reversal per transaction (unique index). Admin only. |
| 4 | Derived vs. stored balance (§12) | A guarded balance column + signed `stock_delta` on every row; `findViolations()` proves they agree (tests + nightly). Pure SUM-on-read cannot give race-safe stock checks at scale. |
| 5 | LOSS / DAMAGE / RECONCILIATION (§11.1 "future" vs §17/§19 "core") | Built as core, for assets *and* consumables. |
| 6 | Roles (§31) | Admin ⊇ everything. Supervisors also issue/return items. Store Staff manage items only if `staffCanManageItems`. Adjustments/loss/retirement are policy-gated. Running/closing a reconciliation and reading reports: admin + supervisor (reading an existing count is open to every role — AUDIT-FINDINGS D3). |
| 7 | Approvals (§18, §32) | Per-operation modes: `direct`, `staff_approval`, `all_approval` (admins never queued). Operations: adjustment, loss, retirement, checkout, check-in. Large-adjustment threshold escalates to `all_approval`. Defaults: adjustment/loss/retirement need approval for staff; routine ops direct (§32). Approvals re-validate against live state. No self-approval. |
| 8 | Checkout override vs. no negative stock (§13.3 vs §38) | Supervisor-authorized override first records an explicit `unrecorded_movement` adjustment for the shortfall, then draws stock down. Stock never goes negative; the gap is visible and attributed. |
| 9 | Location vs. job/site (§9, §10) | `locations` (stores/areas; item home location; `location_id` on every transaction; MVP = 1 active store via `MAX_LOCATIONS_PER_ORG`) are separate from `jobs` (optional context on a transaction). |
| 10 | Quantities | Whole numbers + a unit label. |
| 11 | Offline timestamps (§11, §21) | `occurred_at` (device claim, clamped against clock skew) and `created_at` (server receive time). Order is by server ledger sequence (`seq`). |
| 12 | Shared devices (§49) | Supervisor/admin registers a trusted device; staff switch with a PIN (never admins; lockout; PIN sessions cannot mint sessions). |
| 13 | Infrastructure | Mail: nodemailer over Mailgun SMTP. Storage: S3-compatible (private buckets, signed URLs) with a local driver for dev/test. Background work: BullMQ on Redis. |
| 14 | Scope | Phase 1 + 1.5 fully built. Phase 2/3 only as structural readiness (location-aware schema, `TRANSFER` not implemented, no public API / WhatsApp / SMS). |
| 15 | Shelves (shelf system) | A shelf is its own table inside a location (`SHF-n` code, optional `cycle_count_days`). A shelf has many categories; a category belongs to exactly one shelf; an item belongs to exactly one category. Shelves and categories are created separately. |
| 16 | Mandatory chain & archive rules | Every item sits under a category and every category under a shelf. New organizations are seeded with a **Main shelf** and a **General** category so nothing is ever unplaced. A shelf cannot be archived while it has active categories (`SHELF_NOT_EMPTY`), nor a category while it has active items (`CATEGORY_NOT_EMPTY`); archived parents accept no new children (`SHELF_ARCHIVED` / `CATEGORY_ARCHIVED`); restoring a category needs an active shelf. Archived records still resolve by scan code for history. |
| 17 | Due dates on consumables | A due date is stored on each issue row. A holder's consumable line shows the due date of the **oldest unreturned issue** (FIFO): returns consume issues oldest-first, computed at read time from the ledger (nothing stored, nothing to drift). `partialReturn`, `issuedQuantity`, `returnedQuantity` and `dueStatus` come from the same query that feeds the overdue list, dashboard and Collections, so the numbers cannot disagree. |
| 18 | Logging scope | Every mutating endpoint writes an audit row (enforced route-by-route by `audit-mutations.test.ts`; only reading your own notifications is allowlisted). Also logged: security events (`auth.login_failed` with reason, `auth.account_locked` once per lockout, `auth.pin_failed`, `auth.password_reset_requested`, `access.denied`) and sensitive reads (`activity.viewed`, `report.viewed`, `report.exported`). Security logging is best-effort: a failed audit write never changes the response a caller sees. An unregistered action name throws in tests and is logged loudly (row still written) in production. |
| 19 | Invite matrix | Admin may invite any role. Supervisors may invite store staff and viewers only, and only while the org setting `supervisorsCanInvite` is on. Staff and viewers cannot invite. Resend, revoke and the invitation list follow the same matrix (supervisors see only invitations they could issue). Re-inviting after a revoke reuses the same user row and **replaces** the role; it can never escalate beyond what the inviter may grant. |
| 20 | Custody read-model | Outstanding / Collections / Dashboard read a trigger-maintained `custody_balances` table (one row per item and holder) instead of aggregating the whole ledger per request. It is *derived*: the ledger stays the only source of truth, the integrity oracle recomputes the table and compares, and it can be truncated and rebuilt at any time. |
| 21 | Email suppression | Hard bounces, spam complaints and unsubscribes reported by Mailgun's signed webhook put the address on a global `email_suppressions` list: queued mail to it is cancelled and the outbox never sends or retries to it again, so one dead mailbox cannot damage the sending domain's reputation. Temporary failures are left to Mailgun's own retries. |

## Additional choices worth knowing

- **Item IDs**: UUID primary key + human-readable `PREFIX-0001` (category prefix; gapless per-prefix counter). `code` (the scannable value) defaults to the Item ID; a custom code may never equal another item's Item ID.
- **Due dates** are fixed at issue time (stored on the checkout row), so a later policy change never rewrites history.
- **Low stock** = quantity ≤ item minimum, else category default; no minimum ⇒ not monitored. Events fire on each *downward crossing*.
- **Discrepancy resolution** is derived live (counts are immutable): matched · adjusted · pending_approval · rejected · unresolved. "Open" = latest count for the item that is pending/rejected/unresolved.
- **Audit**: every ledger row also writes an audit event (previous/new state, reason, transaction) in the same DB transaction.
- **Validation**: JSON bodies are strict (no coercion, no unknown fields); query strings are coerced.
- **Dashboard "today"** is the organization's local day (`organizations.timezone`, default `Africa/Lagos`).

### Derived choices (made while building decisions 15–19; defaults the product owner may change)

- **Item location is derived from its shelf.** The client never supplies `locationId`; moving a category to another shelf moves its items' location (and the move is audited).
- **Near-minimum band**: an item is *near* when `minimum < quantity <= minimum + ceil(minimum × nearMinimumPercent / 100)`. Default 10% (`nearMinimumPercent`, 0 disables). Quantity equal to the minimum is *low*, never *near*; a minimum of 0 or unset is never near; assets are never near. Low items sort before near items.
- **Cycle counts** use only **closed, shelf-scope** reconciliations: they set `lastCountedAt`; `nextCountDueAt = (lastCountedAt or shelf created) + cycleCountDays`. One reminder per cycle (dedupe key includes the due instant); changing the interval opens a new cycle. Empty shelves, archived shelves and shelves whose items are all archived are never reminded. *Open question:* closing a shelf count with zero items counted still resets the clock; see AUDIT-FINDINGS D1.
- **Notification routing** is per type and per role (defaults: admin + supervisor). `approval_decided` (goes to the requester) and `announcement` (has its own audience) are not routable. A rule change applies to events not yet fanned out; delivered notifications are never rewritten. Pending invitees and deactivated users never receive anything.
- **Announcements**: audience (roles) is fixed at publish time, empty = everyone; retracting removes *unread* copies and keeps read ones as history. E-mail is off unless `sendEmail`; a user's own e-mail preference beats the announcement's flag in both directions. Title and body are HTML-escaped in e-mail.
- **E-mail ordering**: the outbox sends oldest-first within a batch, so a superseded invite or reset link is never delivered after its replacement (AUDIT-FINDINGS C1).
